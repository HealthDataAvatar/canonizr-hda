# Canonizr Portal — Design Context

## Users

Developers integrating a document-to-markdown API. They arrive to get an API key, check usage, and leave. Maybe they're here to read docs. They spend most of their day in code editors and terminals. They value speed, clarity, code examples with progressive information, and not being patronized. They have zero patience for marketing fluff or UI that makes simple things complicated.

## Brand Personality

**Direct. Precise. Unhurried.**

Canonizr does one thing — converts documents to markdown — and the portal should reflect that single-mindedness. This is portal.canonizr.com — the developer portal, not the marketing site. There is no landing page here. Unauthenticated users land on the auth page, which has a brief explanation of the service and a link to the main canonizr.com marketing site for those who want to learn more.

## Aesthetic Direction

**Utilitarian monochrome with orange punctuation.**

The portal is a tool, not a product showcase. Think of a well-typeset technical manual: generous margins, clear hierarchy, nothing decorative. Orange appears only where the interface needs your attention — a primary action, an active state, a critical number. Everything else is black, white, and gray.

Each page should have exactly one focus, and ideally fit on one desktop screen.

**References:**
- Stripe's developer portal: information density without clutter
- Linear's app chrome: thin header, simple views, clear separation of features
- Vercel's dashboard: system-respecting theme, monospace where appropriate, quiet confidence

**Anti-references:**
- Azure Portal: overwhelming nav, dense iconography, unclear hierarchy, too many competing panels
- Generic SaaS landing pages: hero illustrations, gradient CTAs, "trusted by" logo bars, three-column feature grids with icons
- AI-generated designs: cyan-on-dark, glassmorphism, gradient text, neon accents

**Theme:** System-respecting (prefers-color-scheme). Light and dark both first-class.

### Color

Achromatic foundation with orange as the sole accent. All neutrals tinted very slightly warm (toward the orange hue) for subconscious cohesion.

```
--accent:        oklch(0.65 0.19 45)     /* a burnt, confident orange — not startup-bright */
--accent-hover:  oklch(0.58 0.19 45)     /* darkens on hover, not lightens */
--accent-subtle: oklch(0.65 0.19 45 / 8%) /* tinted backgrounds for emphasis */

Light mode neutrals (hue ~45, chroma 0.005–0.01):
--background:    oklch(0.985 0.005 45)
--foreground:    oklch(0.15 0.01 45)
--muted:         oklch(0.55 0.008 45)
--border:        oklch(0.90 0.005 45)
--surface:       oklch(0.97 0.005 45)    /* code blocks, table headers */

Dark mode neutrals (hue ~45, chroma 0.005–0.01):
--background:    oklch(0.13 0.005 45)
--foreground:    oklch(0.93 0.008 45)
--muted:         oklch(0.55 0.008 45)
--border:        oklch(0.25 0.005 45)
--surface:       oklch(0.18 0.005 45)
```

Orange is used for: primary buttons, active nav indicators, focus rings, inline links, and key metrics. Nothing else. If more than ~10% of pixels on any screen are orange, there's too much.

### Typography

Two families, both served via `next/font/google`:

- **Body/UI:** Source Sans 3 — humanist, highly legible at small sizes, extensive weight range (300–900). Not overused in dev tooling. Warm without being soft.
- **Code/data:** JetBrains Mono — purpose-built for code, distinguishes similar glyphs (0/O, 1/l/I), has ligatures disabled by default. Used in code blocks, API keys, usage numbers, and the curl example.

Monospace is used functionally (actual code, actual data), never decoratively. Headings and body are always Source Sans 3.

Type scale (fixed rem, not fluid — this is an app, not a magazine):
- Page title: 1.5rem / 600
- Section heading: 1.125rem / 600
- Body: 0.9375rem / 400
- Small/label: 0.8125rem / 500
- Code: 0.875rem / 400

Line height: 1.5 for body, 1.3 for headings, 1.6 for code blocks.

### Layout

- **No landing page.** This is portal.canonizr.com. The root `/` redirects to `/dashboard` (authenticated) or `/auth` (unauthenticated).
- **Auth page (`/auth`)** is a standalone centered layout — no sidebar. Brief tagline ("Convert documents to Markdown"), sign-in options, and a small "Learn more at canonizr.com" link for newcomers.
- **Sidebar nav for all authenticated pages.** A narrow (~220px), fixed left sidebar with text links to: Dashboard, API Keys, Billing, Playground, Docs. The sidebar is persistent and always visible on desktop — developers shouldn't have to hunt for pages. Logo/wordmark at the top, user email + sign out at the bottom. Minimal: text links only, no icons, active state is font-weight 600 + orange text.
- Spacing rhythm: 8 / 16 / 24 / 48 / 64. Use 48px between major sections, 24px between related groups, 8–16px within groups.
- Tables over cards for tabular data (keys list, request history). Cards only for singular summary values (usage stats).
- Code blocks: full-bleed within their container, `surface` background, no border, generous padding (1.25rem).

### Interaction

- No modals except for dangerous actions (deletion).
- Loading states: pulsing skeleton lines matching the content shape, not spinners.
- Copy-to-clipboard on API keys and code examples: click the value, it copies, brief "Copied" tooltip, done.
- Empty states teach: "No API keys yet. Create one to start converting documents."

### Responsive

- Mobile is a first-class experience, not a shrunk desktop. The full onboarding flow (sign up, get key, copy it, make first request) must work flawlessly on a phone.
- Below 640px: hamburger menu
- Stat cards stack vertically on mobile. Tables get horizontal scroll.
- API keys and code examples must have large, obvious tap-to-copy targets on mobile — not tiny clipboard icons.
- Touch targets minimum 44px. Generous padding on all interactive elements.

## Design Principles

1. **One thing per screen.** Every page has a single purpose. If you're explaining what the page does, the page is too complex.
2. **Text over chrome.** A well-written sentence beats an icon. A label beats a tooltip. Inline text beats a modal.
3. **Quiet until needed.** Orange appears at the point of action, nowhere else. Motion is reserved for state changes, not decoration.
4. **Developer-native.** Monospace for code, not for vibes. Copyable values everywhere. Curl examples, not SDK wrappers.
5. **Respect the clock.** No onboarding wizard, no welcome modal, no tour. Sign in, see your key, start building.
